# Optional Microsoft email connection

The dashboard does not require Microsoft login. This setup is needed only to send emails. Existing app registrations and the callback URL can be reused; no owner Object ID is required.

The mailbox connection uses a single-tenant Microsoft Entra **Web** application and delegated Microsoft Graph permissions. It is intended for your organisation's work/school accounts with Exchange Online mailboxes in Microsoft's global cloud. Personal Outlook.com sign-in and shared-mailbox sending are not configured.

## 1. Register the application

In the [Microsoft Entra admin center](https://entra.microsoft.com/), select your organisation, then **Entra ID → App registrations → New registration**. Name it `WTD Lead Workspace` and choose the single-tenant option for accounts in your organisation. Record the **Application (client) ID** and **Directory (tenant) ID** from Overview. See [Microsoft's registration guide](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app).

Under Authentication, add a **Web** platform with this redirect URI:

```text
http://localhost:3000/api/auth/microsoft/callback
```

The backend exchanges the code with a client secret, so select Web. Leave implicit access-token/ID-token grants and public-client flows disabled. Register the identical HTTPS callback when deploying. See [Microsoft's redirect URI setup](https://learn.microsoft.com/en-us/entra/identity-platform/how-to-add-redirect-uri).

Under **Certificates & secrets**, create a client secret and copy its **Value**, not its Secret ID, into your backend configuration. Record its expiry for administrator renewal. Microsoft recommends certificate credentials over secrets for production; this project's current configuration implements client-secret authentication. See [credential setup](https://learn.microsoft.com/en-us/entra/identity-platform/how-to-add-credentials).

## 2. Configure delegated permissions

Under **API permissions → Add a permission → Microsoft Graph → Delegated permissions**, configure:

| Permission | Used for |
| --- | --- |
| `User.Read` | Read the signed-in person's profile and mailbox address through `/me` |
| `Mail.Send` | Send reviewed messages from that person's mailbox through `/me/sendMail` |

MSAL also requests the OpenID scopes `openid`, `profile`, and `offline_access` during sign-in. They support identity validation and refresh-token use. Do not configure application-wide Mail.Send for this workflow. Ask your administrator to grant consent if the organisation's consent policy requires it. The dashboard has no Microsoft login gate or workspace allowlist. Microsoft tenant policy still controls who can consent to mailbox access. A pending Microsoft consent request affects email only; you can continue using the workspace.

Sources: [Graph profile permissions](https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0), [Graph mail permissions](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0), [MSAL token acquisition](https://learn.microsoft.com/en-us/entra/msal/python/getting-started/acquiring-tokens).

## 3. Configure optional email

No owner ID or user approval configuration is needed.

Run `python setup_local.py` in the project root, then set:

```dotenv
# Root .env — keep all of these on the server
MICROSOFT_TENANT_ID=your_directory_tenant_uuid
MICROSOFT_CLIENT_ID=your_application_client_uuid
MICROSOFT_CLIENT_SECRET=your_secret_value
MICROSOFT_REDIRECT_URI=http://localhost:3000/api/auth/microsoft/callback
# Keep the TOKEN_ENCRYPTION_KEY generated by setup_local.py.
DAILY_SEND_LIMIT=30
```

`MICROSOFT_ADMIN_OBJECT_IDS` from the previous version is ignored and can be deleted. Keep the existing `API_KEY` and encryption key; running setup preserves non-empty values.

In `frontend/.env.local`:

```dotenv
BACKEND_URL=http://127.0.0.1:8000
API_KEY=the_same_api_key_as_the_backend
DASHBOARD_ORIGIN=http://localhost:3000
COOKIE_SECURE=false
```

Restart both servers and open **http://localhost:3000**. Do not alternate between `localhost` and `127.0.0.1`: origin checks and callback cookies depend on the configured hostname.

## 4. Connect a mailbox when needed

Open the dashboard directly. In **Connections**, click **Connect Microsoft mailbox**, choose your organisation's account and complete consent. You return to Connections with your verified mailbox address. Cancelling or failing the connection keeps the dashboard available. If Microsoft shows Request pending, your tenant administrator must approve the requested permissions for email. App ownership alone does not grant tenant consent authority.

The mailbox connection still verifies the ID token's signature, issuer, audience, expiry, tenant and immutable user Object ID; MSAL validates state/nonce and uses PKCE. These checks bind the sending capability to the correct mailbox. [Microsoft ID-token claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference).

Each browser has its own optional connection. Disconnect it using **Connections → Disconnect mailbox**. This invalidates that connection immediately; the final active connection for a mailbox also deletes its cached tokens and clears its unsent approvals. Lead data and editing remain available. No invitation, approval or connection action sends email.

The workspace has no account roles. Only the connected sending mailbox can resolve an uncertain send, after checking Sent Items or Exchange trace. Another mailbox must freshly approve a draft to send it. All visitors who can reach the frontend share the workspace data; restrict deployment access separately if needed.

## 5. Email and token lifetime

Review the recipient, content and displayed From account. Turn on **Ready to send**, then click **Send email**. Graph sends from the connected account's mailbox and saves to Sent Items; the UI cannot supply another From address. `SENDER_EMAIL` only controls generated signature text. A Microsoft `202` means acceptance for processing, not proof of final delivery. [sendMail behavior](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0).

Microsoft access tokens are acquired silently from the encrypted per-user MSAL cache; MSAL uses the refresh token when needed. No daily access-token paste or scheduled renewal job is required. Refresh tokens can expire or be revoked, and tenant policies can require interactive sign-in again. Reconnect in Connections if Microsoft requests it. The mailbox connection expires after eight hours; expiry does not close the dashboard or block research. [Microsoft refresh-token behavior](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens).

The Entra **client secret** has its own administrator-configured expiry. Automatic access-token renewal does not extend that secret. Replace the secret value and restart the backend when you rotate it. This is separate from the ZoomInfo app credentials described in [ZOOMINFO_SETUP.md](ZOOMINFO_SETUP.md).

Keep `TOKEN_ENCRYPTION_KEY` stable and backed up outside the database. Losing/changing it requires reconnecting the mailbox. Sessions are opaque random values stored as hashes; provider tokens and mailbox authorization flows are encrypted in SQLite and never returned to the browser. [MSAL cache persistence](https://learn.microsoft.com/en-us/entra/msal/python/advanced/msal-python-token-cache-serialization).

## Hosting and verification

Use one backend worker and keep this login-free frontend on a trusted private network or behind an access layer. With an HTTPS deployment, set the public `DASHBOARD_ORIGIN`, `COOKIE_SECURE=true`, and matching `MICROSOFT_REDIRECT_URI` in both Entra and the backend. Keep the backend API key private and FastAPI behind Next.js. OAuth callbacks use a one-use flow cookie, a fixed return URL, and no-referrer/no-store responses. Configure proxy logs not to retain callback query strings.

For an Unknown email outcome, inspect the sending mailbox's Sent Items or Exchange trace by sender, recipient and time. The app's delivery reference is a custom `x-wtd-delivery-id` header, not Exchange's internet Message-ID. Do not assume a missing Sent Item immediately proves non-delivery; ask the Exchange administrator if uncertain.

Local tests cover real MSAL state/nonce/PKCE and refresh handling against a simulated provider, cryptographic token rejection, direct workspace access and mailbox disconnection, and Graph request/error handling. Your tenant registration, consent policy and actual mailbox delivery still require verification using your account; no real credentials or messages were used during development.
